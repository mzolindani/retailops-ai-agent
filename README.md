# RetailOps AI Agent

A local-first retail operations AI agent built with Python, LangChain's `create_agent`, LangGraph, Ollama, and PostgreSQL. The agent uses a ReAct-style tool-calling workflow to answer retail operations questions by querying structured database records through deterministic Python tools.

The current milestone supports **read-only product, inventory, order, and fulfilment queries**. The agent does not create or modify orders, change inventory, process refunds, or cancel orders.

## Features

- **Product search:** Search products by product ID or product category, including English category translations.
- **Inventory lookup:** Retrieve available and reserved quantities for a product at a specified store.
- **Order lookup:** Retrieve order details and associated order items.
- **Order item analysis:** Inspect products, quantities, prices, and seller information associated with an order.
- **Fulfilment checks:** Retrieve order and inventory information to help assess whether an order can be fulfilled.
- **PostgreSQL integration:** Query structured retail data using Python database tools.
- **Local LLM inference:** Run the agent with Ollama without requiring a hosted LLM API.
- **Controlled tool execution:** Database access is handled by predefined Python functions rather than unrestricted SQL generated by the model.

## Architecture

The agent follows a tool-calling workflow:

1. A user submits a retail operations question through the command-line interface.
2. The LangChain agent interprets the request and decides which tool or tools to call.
3. The selected Python tool queries PostgreSQL.
4. The tool returns structured results to the agent.
5. The model uses those results to formulate a natural-language response.

The model handles reasoning and tool selection. The Python tools and PostgreSQL database provide the underlying data.

## Database

The project uses a PostgreSQL database named `retailops` with the following tables:

| Table | Purpose |
|---|---|
| `products` | Product identifiers and product categories |
| `product_category_name_translation` | Maps Portuguese product category names to English |
| `inventory` | Available and reserved stock by product and store |
| `orders` | Order status, timestamps, and delivery-related information |
| `order_items` | Products, quantities, prices, and seller information associated with orders |

The product, order, and order-item tables use data from the Olist Brazilian e-commerce dataset. The inventory table contains separate store-level stock records used for inventory lookup and testing.

**Data limitation:** The Olist product data primarily contains product IDs and category information rather than descriptive product names or retail SKUs. The agent must not invent missing product names, inventory records, or stock quantities.

## Windows PowerShell Setup

### 1. Install Ollama and pull a model

Install Ollama from https://ollama.com/download/windows.

Open PowerShell and run:

```powershell
ollama pull qwen2.5:3b
ollama list
```

Ensure Ollama is running before starting the agent.

### 2. Set up the Python environment

From the project directory:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1

python -m pip install --upgrade pip
pip install -e ".[dev]"
```

If PowerShell blocks virtual environment activation, run:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

Then activate the environment again.

### 3. Configure the database connection

Copy the example environment file:

```powershell
Copy-Item .env.example .env
```

Update `.env` with the connection details for your PostgreSQL database:

```dotenv
PGHOST=localhost
PGPORT=5432
PGDATABASE=retailops
PGUSER=your_database_user
PGPASSWORD=your_database_password
```

Replace the example credentials with your actual PostgreSQL settings. Do not commit `.env` or expose database credentials in source control.

Ensure the configured database user has the necessary permissions to read the tables used by the agent.

## Running the Agent

Activate the virtual environment and run a question through the CLI:

```powershell
python -m app.cli "Show me the details and delivery status of order e481f51cbdc54678b7cc49136f2d6af7"
```

The agent will process the question, call the appropriate database tool, and return an answer based on the retrieved data.

## Example Queries

### Product search

```powershell
python -m app.cli "Find five products in the housewares category"
```

```powershell
python -m app.cli "Find products in the computers category"
```

### Inventory lookup

```powershell
python -m app.cli "Check the stock availability of product 1e9e8ef04dbcff4541ed26657ea517e5 at STORE-01"
```

```powershell
python -m app.cli "Check the stock availability of product 96bd76ec8810374ed1b65e291975717f at STORE-01"
```

The inventory response distinguishes available quantities from reserved quantities. A missing inventory record does not necessarily mean that a product is out of stock.

### Order lookup

```powershell
python -m app.cli "Show me the details and delivery status of order e481f51cbdc54678b7cc49136f2d6af7"
```

### Order items

```powershell
python -m app.cli "Show me the items associated with order e481f51cbdc54678b7cc49136f2d6af7, including product IDs, quantities, and prices"
```

### Fulfilment assessment

```powershell
python -m app.cli "Summarise order e481f51cbdc54678b7cc49136f2d6af7, including its status, number of items, and total item value"
```

The agent should use the available order and order-item data to answer the request. A reliable fulfilment assessment also requires inventory records that correspond to the relevant products and store.

## Testing

Run the automated tests:

```powershell
pytest -q
```

The deterministic Python tools can also be tested independently of the LLM.

For example:

```powershell
python -c "from app.tools import lookup_products; print(lookup_products('housewares', 5))"
```

```powershell
python -c "from app.tools import get_inventory; print(get_inventory('1e9e8ef04dbcff4541ed26657ea517e5', 'STORE-01'))"
```

```powershell
python -c "from app.tools import get_order; print(get_order('e481f51cbdc54678b7cc49136f2d6af7'))"
```

Direct tool tests help distinguish database or query issues from model tool-calling issues.

## Design Decisions

- **Tool-based architecture:** The model chooses among predefined tools rather than generating unrestricted database queries.
- **Deterministic data access:** Python functions own the SQL queries and return structured results.
- **Read-only scope:** The current agent does not expose database mutation operations.
- **Grounded responses:** The agent should base answers on retrieved records and clearly identify missing data.
- **Local inference:** Ollama runs the model locally, reducing reliance on hosted model APIs.
- **Separation of concerns:** The agent manages reasoning and tool selection, while database tools handle retrieval and data access.

## Current Limitations

- Product records may not contain human-readable product names or SKUs.
- Inventory results depend on the availability of matching product and store records.
- Order fulfilment assessments depend on the completeness and accuracy of inventory data.
- Local models can occasionally select the wrong tool, misinterpret a result, or fail to call a tool.
- The agent is not yet a transactional inventory management system and cannot perform stock updates, refunds, or cancellations.

## Troubleshooting

### Ollama is unavailable

Check that Ollama is installed, running, and that the model is available:

```powershell
ollama list
```

### Database connection fails

Verify the values in `.env`, confirm PostgreSQL is running, and check the database name, credentials, port, and user permissions.

### Inventory lookup returns `inventory_not_found`

Confirm that the product exists in `products` and that a matching `(product_id, store_id)` record exists in `inventory`. A missing record should not automatically be interpreted as zero stock.

### The agent returns an incorrect or incomplete result

Test the corresponding Python tool directly. If the tool returns correct data but the agent does not, inspect the tool descriptions, the registered `AGENT_TOOLS`, the agent instructions, and the model's tool-calling behaviour.
